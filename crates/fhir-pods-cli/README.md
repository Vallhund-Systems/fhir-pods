# fhir-pods CLI

A local command-line pod over the Rust core, with no dependencies beyond the
core and the standard library. It performs no network calls.

Build or install from the repository root:

```sh
cargo build --release -p fhir-pods-cli
cargo install --path crates/fhir-pods-cli
```

```sh
fhir-pods validate patient.json
fhir-pods validate --outcome < patient.json
fhir-pods lower http://hl7.org.au/fhir/core/StructureDefinition/au-core-patient inputs.json
fhir-pods lift http://hl7.org.au/fhir/core/StructureDefinition/au-core-patient patient.json
fhir-pods lift "" < patient.json
fhir-pods deidentify --policy policy.json patient.json
fhir-pods document ips inputs.json
fhir-pods document au-ps < inputs.json
fhir-pods audit read audit-inputs.json
fhir-pods audit patient-query < audit-inputs.json
fhir-pods v2 message.hl7 --timezone +10:00 --code-system LOCAL=https://example.org/codes
fhir-pods v2 --structure ORU_R01
fhir-pods needs patient.json
fhir-pods needs --terminology terminology.txt patient.json
fhir-pods slots http://hl7.org.au/fhir/core/StructureDefinition/au-core-patient
fhir-pods must-support patient.json
```

Input defaults to stdin; an explicit `-` also means stdin. Each invocation
accepts one JSON input, or ER7 text for `v2`. `slots` and `v2 --structure`
read no input. Put `--` before a positional filename beginning with
`-`. A policy may come from stdin when the resource comes from a file. Two
inputs cannot share stdin. The CLI does not accept a salt as a command-line
option: the policy file has the same shape as the core's policy JSON:

```json
{"salt":"host-supplied-secret","today":"2026-09-16","base":"safe-harbor"}
```

Results go to stdout as one JSON object. `validate --outcome` emits a FHIR
OperationOutcome; default validation emits the pod report. `lower`,
`audit`, `deidentify`, and `document` use the same result shapes as the WASM pod,
including the output resource, validation and operation-specific findings.
De-identification includes both `remaining` (the bounded identifying-field
check) and `residual` (free text kept by the policy). A nonempty `residual`
is reported even when validation passes and `remaining` is empty; it does
not change the exit-code rules below.
`needs` emits both `needs` and `validation`, so an invalid input cannot look
successful merely because it has no terminology questions.

`--terminology TABLE` supplies a local compiled terminology table to `validate`,
`lower`, `lift`, `document`, `audit`, `v2`, `needs`, or `must-support`. The format
is the core's `fhir-pods-terminology 1` line format, generated by
`tools/compile_valueset.py` from an expansion. Each set included in the table
must be complete: an unlisted code is a nonmember. An absent set is unresolved.
Bundled sets answer first; the supplied table answers the remaining questions.
`needs --terminology TABLE` returns only questions still unresolved after both.
Lowering can also obtain coding displays from the table. Tables apply to this
invocation only; no network requests or persistent terminology state are used.
`TABLE` may be `-` when the resource is read from a file. A missing, non-UTF-8,
empty or malformed table is a configuration error (exit 2), checked before
reading the resource. Repeat `--terminology` is a usage error; combine sets in
one table. The core's `deidentify` API uses bundled terminology only, so this
flag is rejected for that command. Revalidate the emitted resource separately
when a supplied table is needed.

`slots PROFILE_URL` emits the compiled profile's input slots as
`{slots: [{path, type, choices, min, max, mustSupport}]}`. `max: null` means
unbounded. A missing URL is a usage error; an unknown profile is a rejected
operation. This is registry inspection, with no resource or terminology input.

`must-support` emits `{mustSupportGaps, validation}`. Gaps are information and
do not change the validation exit code. The validation report also preserves
invalid-input errors and unsupported-profile warnings, so an empty gap list
does not imply that a profile was checked.

`lift PROFILE_URL` reads a resource into the profile's input slots for `lower`.
Pass an empty argument (`lift ""`) to select a compiled profile declared in the
resource's `meta.profile`. With an explicit URL, the resource is validated
against that profile even when it does not declare it. The result contains
`inputs` (an object, not an encoded JSON string), `validation`, `missing`
(required slots absent) and `extras` (paths not covered by slots, fixed leaves
or pass-through fields). A valid verdict can still include missing slots;
the exit code checks both fields. Nonempty `extras` do not change the exit code;
inspect them before lowering the returned `inputs`, since uncovered values are not
preserved. A missing CLI profile argument is a usage error (exit 2); an unknown
profile, absent compiled declaration with `""`, wrong resource type or malformed
resource is a rejected operation (exit 1, JSON error on stdout).

`audit KIND` builds a BALP basic AuditEvent from host inputs. Kinds are `read`,
`query`, `create`, `update`, `delete`, and the five `patient-` prefixed variants.
For example, `fhir-pods audit read` accepts this JSON on stdin:

```json
{
  "recorded": "2026-09-16T10:00:00Z",
  "client": {"who": "Device/app", "network": "10.0.0.7"},
  "server": {"who": "Device/server", "network": "https://fhir.example.org/r4"},
  "source": {"observer": "Device/audit-collector"},
  "data": "Observation/example"
}
```

For queries, replace `data` with `query` (the original query text; the core
base64-encodes it). Patient variants also require `patient`, such as
`"patient": "Patient/example"`. Optional `user` and `transaction` inputs identify
the actor and request. The result contains `resource` and `validation`.
These BALP basic events describe successful actions; failed actions can be
constructed with `lower http://hl7.org/fhir/StructureDefinition/AuditEvent`.
A missing or unknown CLI kind is a usage error (exit 2); rejected host inputs
or an invalid generated record return exit 1 with a JSON error/report.

`v2` converts one HL7 v2 ER7 message through the compiled maps and returns
`{bundle, validation, skipped, unplaced, unmapped}`. It passes input bytes
unchanged to the core, which accepts CR, LF and CRLF segment separators.
Generated identifiers depend on those bytes; changing line endings can change
identifiers. Transport framing such as MLLP belongs to the caller.

`--timezone Z|+10:00` supplies the zone for timestamps that omit one; existing
zones remain in place. Without it, the core truncates such times to dates and
reports the limitation. Repeat `--code-system NAME=URI` for distinct local
coding-system names. The core validates the option values before input is read;
malformed or repeated options are usage errors (exit 2).

`skipped` describes map rows that could not be applied, `unmapped` names valued
fields that the maps do not cover, and `unplaced` names segments that the
message structure cannot place. Every list is returned intact. A valid bundle
with skipped/unmapped data can exit 0; inspect those lists when deciding whether
the conversion meets the host's needs. Nonempty `unplaced` causes exit 1 even
when bundle validation succeeds. Missing required FHIR content stays visible
in the returned validation; the CLI does not fill it in. A message that cannot
start conversion returns a JSON error with exit 1.

`v2 --structure NAME` emits `{structure, tree}`, where `tree` is the core's
message-structure description as a JSON string. It does not consume stdin and
cannot be combined with a file, conversion options or a terminology table.

| Exit | Meaning |
| --- | --- |
| 0 | Valid result or successful inspection. De-identification additionally requires empty `remaining`; lifting requires empty `missing`; v2 conversion requires empty `unplaced`. |
| 1 | Invalid result, remaining de-identification findings, missing lift slots, unplaced v2 segments, or input rejected by the operation. The JSON report/error is on stdout. |
| 2 | Usage, policy/terminology configuration, file/stdin read, or detected output failure. Usage/read/configuration errors are JSON on stderr; an output failure cannot guarantee delivery of an error. |

Warnings do not change the validation verdict. In particular, a successful
`needs` invocation can list unresolved terminology for the host to supply.
The core's de-identification checker has a bounded scope; an empty `remaining`
list is not an independent certification of privacy. Inspect all operation
results before choosing to use the output.

`--help` and `--version` return plain text. No output file is overwritten by
the CLI; use the shell's redirection when desired.

Unix output writes preserve errors from read-only descriptors and broken pipes.
Rust's startup code can reopen an inherited closed standard stream on
`/dev/null` before the CLI starts; shell redirection such as `1>&-` can therefore
discard output while the command exits 0. Exit status alone cannot establish
that a consumer received the JSON. This startup behavior is documented in
[Rust's Unix runtime](https://doc.rust-lang.org/src/std/sys/pal/unix/mod.rs.html).
The output regressions run on Unix; other platforms retain standard Rust I/O.
